# Exposure ledger

Every model or tool touch (including a single-sample smoke) gets a row **before results are read**.
Exposure claims elsewhere must carry four fields: scope, date, counts, inherited exposure.

Field semantics (consolidated contract §6/§7; umbrella 续92/续93):

- `execution profile` — one of `model-free-check` / `baseline-reproduction` /
  `bounded-discovery-probe`; paper-scale profiles never appear in this ledger.
- `split role` — `discovery` or `dev`. `confirmatory` rows require Stage-3 paper authority
  (`OWNER_GO_AND_PAPER_EXECUTION_CONTRACT`) or a dated owner allowance and do not occur in Stage-2.
- `split identity hash` — SHA-256 over the exact sample-identity list this touch may read.
- `consumed` — `yes` only when confirmatory results were read; **irreversible once `yes`**;
  model-free and discovery/dev rows write `no`.
- `inherited exposure` — scoped statement of prior exposure carried into this touch;
  monotonically non-decreasing across rows.
- `calls` / `speech audio seconds` / `gpu hours` — the registered budget record for this
  run; every cell must be a **finite non-negative number** (the gate refuses NaN or
  negative cells outright — they would corrupt the arithmetic). These columns carry no
  numeric ceiling of their own (the first-slice caps that used to sum them as slice
  totals — consolidated contract §6 — were retired by the 2026-08-06 owner amendment,
  `SAEA-OWNER-AMENDMENT-2026-08-06-BUDGET-CAPS`): `contracts.FrozenCoreGate` no longer sums
  these columns across rows. What it still enforces, per row, is the cross-check that a
  plan may only claim what its OWN matched row registers: `registered ≥ planned` for each
  of the three columns, against the plan's own declared `planned_model_calls` /
  `planned_speech_audio_seconds` / `planned_gpu_hours`.

Earnings21/Earnings22/ConEC model exposure inherited as of 2026-08-03). The carriers' only

Cause: VRAM headroom — `-c 32768 -np 4` reserved 8k KV per slot against slices that need ~1.5k, leaving ~500 MB free on a 24 GB card. Fix attempt 1 (protocol-bound, new config hash): `-c 16384` (4k/slot). **That fix was itself WRONG and was stopped after 81 calls / 4,860 audio-s (attempt `attempt-20260809T112222Z-30ca91`, left OPENED when the operator killed it deliberately, before any result was read).** Reason for stopping: measurement showed the ConEC evidence materials the matched/mismatched arms inject run to 23.3 KB (~5,835 tokens; median 7.4 KB ≈ 1,850), so a worst-case evidence request needs ≈7,000 tokens — more than the 4,096/slot that `-c 16384 -np 4` provides. Letting it run would have completed the no-evidence arm and then failed the two evidence arms, invalidating the whole paired set (all three arms must share one config hash). A systematic memory strategy is being measured instead (KV quantization, CPU-RAM KV fallback using the 43 GB of idle system memory, partial layer offload, and a stable-prefix prompt ordering so a call's evidence block is prompt-cached once rather than re-sent per slice); all three arms then re-run together under one new hash. Both aborted/stopped attempts' spend stays on record here. **2026-08-09 third stop (before any result read): the first final-config attempt of the `nocontext` arm was killed at 86/610 slices after a 7.3× throughput collapse — first quarter 9.9 s/slice, last quarter 72.1 s/slice.** Cause: an ops agent's diagnostic process took a ~715 MiB CUDA context beside the run (it had assumed `-dev none` prevents a context; it does not), squeezing free VRAM to ~350 MiB; with `-ngl 999` disabling llama.cpp's device-memory fitting, allocations spill to host memory under pressure and are never migrated back, so throughput stayed degraded for 12+ minutes after the competing process died. Scientifically the outputs are unaffected (memory placement does not change arithmetic), but at 72 s/slice the three arms would have taken 30+ h instead of ~5 h, so the sequence was restarted on a verified-empty GPU (0 MiB, 0 compute apps). Standing rule adopted: **no process that can open a CUDA context may run beside a live experiment, diagnostics included.** **2026-08-09 fourth stop — a PROTOCOL DEFECT, not an environment one (before any result read):** the clean-GPU rerun of `nocontext` aborted at 581/610 with the same `[100054] asr … timed out`, and the earlier attempt aborted at 577 — a deterministic failure at ~578±3 on a specific input, with all 579 preceding slices healthy (15–16 s each, the last one 3.9 s). Root cause: **the model config declared no generation cap**, so a degenerate slice (silence/music/applause at a call's tail) can run away and generate until the 12,288-token slot fills — ≈600 s at ~20 tok/s — which exceeds even the 900 s transport ceiling, so the bounded per-slice retry could not help either (the retry would burn another 900 s the same way). Fix, protocol-bound and therefore a new config hash: `max_tokens: 1024` in `decoding_params` (≈4–5× the observed 146–250-token slice output, so legitimate transcripts are untouched) and `timeout_seconds` 900 → 240 (≈15× a healthy 16 s slice), which makes a runaway cost ~50 s and lets the retry actually recover. Confirmed: exactly one asr invocation never returned (580 `ability_start` events against 579 `ability_end`), and the arm aborted the instant that invocation's retry budget was exhausted. Wrong: it is **not** "a deterministic failure at ~578±3 on a specific input". The two aborted attempts hung on *different* samples (`4366429` in `96ccb8`, `4387383` in `1c09ee` — each attempt wrote 9 of the 10 per-sample derivation files, missing exactly the sample that hung), and the slice ordinal is incidental because `obs_batch_samples: 4` runs four samples concurrently. Nor was anything degrading: across all 580 requests the longest start→end gap was 38.6 s, and the run spanned 1.87 h, not the ~9 h a naive reading of the call count suggests. The fix stands and its rationale is strengthened: with no `max_tokens`, llama.cpp decodes until the slot's 12,288-token context fills, and because decoding is deterministic (temperature 0, fixed seed) the single bounded retry re-sent a byte-identical request and hung identically — **a bounded retry can only recover *transient* failures, never content-deterministic ones**, so capping generation is what actually makes the worst case finite. Consequence for reading the rerun: a slice whose completion is exactly 1024 tokens is a saturation flag rather than a transcript, and must be counted and reported, not scored silently.
