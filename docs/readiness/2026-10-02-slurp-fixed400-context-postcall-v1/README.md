# Fixed 400-input optimization pool: context and post-call handling

Owner224 supersedes the proposed fresh-panel sequence for optimization. Keep the existing UPDATE2 roster, in its current order, and use its first 20, 50, 100, 200 and 400 inputs. The current pilot is exactly the first 20. This is one reused optimization pool, not five independent datasets. Do not rebuild audio, packets, knowledge releases or the underlying dataset. [Pinned panel plan](plan.json) records identities and nesting without copying task data.

## Why focus here

The earlier qualified node-information ledger reports delivered slot-type cards for 928 of 941 gold items. This is evidence of broad type coverage in that earlier cohort, not proof that every input has sufficient or correctly consumed evidence. It supports freezing the present knowledge assets while testing better organization and use. Do not feed this combined historical/root diagnosis to a feedback-blind proposer.

The current qualified 8x20 pilot has 289 valid raw Reviewer JSON handoffs, but 17 of 339 findings contain non-slot identifiers. Of 289 Solver contacts, 27 do not have the exact task JSON shape and 24 contain textual tool-call markers. Those markers are not authorized tool executions. All eight members have zero actual knowledge calls. These are actionable mechanism observations; they do not establish that a parser change or more tool calls will improve terminal SLU-F1.

## Existing rails paths and the next optimization targets

| Seam | Verified current behavior | Next target |
| --- | --- | --- |
| Before a call | Task/knowledge/context assembly and role controls; constant tool-schema rendering | Separate task evidence, knowledge examples, role authority and unresolved doubts; remove irrelevant duplication without deleting needed evidence |
| After Reviewer | `normalize_review_handoff` seals a normalized state while retaining raw-response provenance | Validate type identifiers and preserve specific actionable doubts, checked facts and unresolved uncertainty |
| After a phase | Optional `review_for_phase` produces structured criticism; native runner emits it to USE; the accepted `on_flag=record` path does not alter successor state or contacts | Make any future model-visible critique an explicit bounded handoff, not an assumption that a recorded flag already influenced the next role |
| At delivery | Existing registered delivery normalizer projects the final Solver text and records input/output hashes | Audit representation changes separately from semantic changes; preserve Omni answer authority and identify lost/altered content |

Semantic repair returns to the existing Solver within the revision budget. A post-call component must not invent a value, substitute a second answering model or convert an example into speech evidence. Record raw reply, normalized state, flags, which next role received them, actual revision and final delivery. Existing closed citation, rule-card and re-listen routes stay closed.

## Reuse and scaling

1. Diagnose the already qualified complete pilot and earlier qualified 400-row families before spending more GPU time. Keep scientific comparisons specific to their own rosters and versions.
2. Improve the actual context/handoff bottlenecks on the fixed small prefix. Use all cases, including unchanged and damaged answers. Learning may revisit them; preserve their exposure history.
3. Expand within the same pool to 50, 100, 200 and 400 after root review. Report each updated version separately; do not assemble a fictitious 400-row result from different policies.
4. Run only informative changed candidates and necessary controls. Repeating the original eight groups after every repair is not the default. To claim an advantage from feedback over blind search, still run a prospectively registered matched L/B comparison; a reduced repair panel alone cannot answer that question.
5. Lock the solution on this optimization pool. Independent confirmation is a later, separately identified activity, not a reason to replace the current working data now.

Previously sealed outputs and official score receipts remain reusable evidence, not permission to rescore or mutate them. New model-facing policies require new bounded attempts and complete-system terminal evaluation. Future runtime admission must distinguish permitted repeated optimization feedback from forbidden runtime labels and independent-validation leakage; the current global ancestry-disjointness check must not simply be disabled.
